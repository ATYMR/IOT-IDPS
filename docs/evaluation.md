# Detection methodology and evaluation

> **All numbers on this page come from SYNTHETIC data** generated by
> `idps/synthetic.py`. The generator encodes my own assumptions about what
> normal behaviour and attacks look like in these counters. The results show
> that the pipeline works and how the detectors compare *under those
> assumptions*. They are **not** evidence of real-world detection performance.
> No real attack traffic has been collected yet.

## What is detected

A *window* is one telemetry report (5 s) from one device. A window is
**anomalous** if its feature vector is unusual relative to normal windows
seen in training. An **attack** label exists only in synthetic data.

| Feature | Derived from | Rationale |
|---|---|---|
| `rx_rate` | `rx_msgs / Δuptime` | Floods on the device's command topic |
| `auth_fail_rate` | `auth_fail / Δuptime` | Forged / replayed / malformed commands |
| `heap_drop_kb` | max free heap since boot − current | Leaks, exhaustion, fragmentation |
| `wifi_reconnects` | Δ cumulative counter | Deauthentication / jamming |
| `mqtt_reconnects` | Δ cumulative counter | Client-id takeover, broker disruption |
| `interval_s` | Δ `uptime_s` between reports | Missed reports, loop starvation |

Deterministic rule findings (malformed payloads, MAC failures, replays,
unknown devices, ≥ 3 rejected commands per window, offline devices) are
handled separately and covered by unit tests, not by these metrics.

## Synthetic data

`python -m idps generate-data --seed 42` produces 3 devices (two ESP32-like,
one ESP8266-like) × 4000 windows ≈ 5.5 simulated hours each.

* **Normal behaviour** includes noise and rare benign events: occasional
  legitimate commands, heap dips from transient allocations, rare Wi-Fi/MQTT
  reconnects, missed reports and benign reboots.
* **Attacks** are injected only in the final 25 % of each stream, as episodes
  of 6-40 windows with a random intensity in [0, 1]. Low-intensity episodes
  overlap with normal behaviour on purpose.

| Attack | Effect on counters |
|---|---|
| `cmd_flood` | Many messages on the command topic; up to 5/s rejected, the rest dropped; heap pressure; occasional loop starvation |
| `forged_cmd` | Low-rate forged commands (brute force); each one rejected |
| `wifi_deauth` | Wi-Fi + MQTT reconnects, reporting gaps |
| `clientid_hijack` | Extra MQTT reconnects (another client using the same client id) |
| `heap_exhaustion` | Growing heap deficit; out-of-memory reboot when < 10 % remains |

**Known bias:** each attack mostly shifts one or two features. This favours
per-feature detectors and cannot demonstrate any benefit from modelling
feature interactions.

## Protocol (no leakage)

1. Every record passes through the production path: JSON validation →
   `DeviceTracker` → feature vector.
2. Per device, **chronological** split: first 60 % train, next 15 %
   validation, last 25 % test. No shuffling.
3. Train and validation use normal windows only (novelty detection). The
   pipeline reports how many attack windows had to be dropped from them (0 for
   the synthetic data).
4. Each detector gets the same false-positive budget (`target_fpr = 0.01`),
   calibrated as a quantile of its scores on the validation windows. The
   ensemble splits the budget equally between its two components.
5. Metrics are computed per window on the untouched test slice. Episode-level
   detection and time-to-first-alert are reported too.
6. `idps benchmark` repeats everything for 10 generator seeds.

## Results

### Multi-seed benchmark (the numbers to quote)

`python -m idps benchmark --seeds 10` (seeds 0-9, 4000 windows/device, target FPR 0.01; mean ± std):

| Detector | Precision | Recall | F1 | FPR | ROC-AUC | PR-AUC |
|---|---|---|---|---|---|---|
| Ensemble (IF + z-score) — default | 0.960 ± 0.013 | 0.654 ± 0.058 | 0.776 ± 0.042 | 0.008 ± 0.003 | 0.881 ± 0.027 | 0.853 ± 0.032 |
| Isolation Forest only | 0.916 ± 0.019 | 0.428 ± 0.115 | 0.575 ± 0.112 | 0.012 ± 0.004 | 0.871 ± 0.027 | 0.797 ± 0.040 |
| z-score only (baseline) | 0.971 ± 0.015 | 0.681 ± 0.040 | 0.800 ± 0.028 | 0.006 ± 0.004 | 0.881 ± 0.026 | 0.853 ± 0.031 |
| Engine (ensemble OR rejection rule) | 0.960 ± 0.013 | 0.654 ± 0.058 | 0.776 ± 0.042 | 0.008 ± 0.003 | n/a | n/a |

### Single run, seed 42 (per attack type)

`python -m idps generate-data && python -m idps train`. Window recall:

| Attack | Windows | Ensemble | IF only | z-score only |
|---|---|---|---|---|
| clientid_hijack | 180 | 0.417 | 0.022 | 0.411 |
| cmd_flood | 149 | 1.000 | 1.000 | 1.000 |
| forged_cmd | 90 | 0.833 | 0.933 | 0.489 |
| heap_exhaustion | 239 | 0.874 | 0.895 | 0.506 |
| wifi_deauth | 132 | 0.538 | 0.045 | 0.538 |

Every one of the 31 test episodes was detected by at least one window; mean
time to first alert was 0-2.4 windows (0-12 s).

Measured scoring latency on the development laptop (Windows 11, Python
3.13, scikit-learn 1.8): about **12.7 ms per single window** (mostly
per-call overhead across 200 trees) and **13 µs per window when batched**. At
one window per device every 5 s, that is far below real-time limits for a
small deployment.

## Interpretation

1. **Isolation Forest alone is the weakest detector here.** It cannot
   extrapolate: values beyond the training range score like the most extreme
   training point. It also rarely splits on features that are zero in most
   bootstrap samples (reconnect counts). Benign rare events therefore use up
   its false-positive budget. That is why it misses most reconnect-based
   attacks (2-5 % recall).
2. **The components are complementary per attack type.** IF is clearly better
   on `forged_cmd` and `heap_exhaustion` (seed 42); z-score is better on
   reconnect attacks. The ensemble combines both.
3. **Across seeds, the ensemble does not beat the simple z-score baseline**
   (F1 0.776 ± 0.042 vs 0.800 ± 0.028; the intervals overlap). Given the
   generator bias above, this is the expected outcome. Seed 42 alone suggests
   the opposite (0.828 vs 0.730): one seed is not enough evidence.
4. **The ensemble stays the default** because it is robust to IF's blind
   spots and keeps a multivariate component for real data. This is a
   judgement call that the current evidence does not settle. `--detector
   zscore` is a defensible alternative.
5. **The rejection rule adds nothing on top of the detector** in this data.
   Every window it fires on is already anomalous. It stays because it is
   deterministic and explainable and keeps working without a model.
6. **Window recall is bounded by the data.** A low-intensity hijack or deauth
   episode has many windows where nothing observable happens. Episode-level
   detection is the more meaningful operational metric.

## What is still needed for a real evaluation

* Normal telemetry from real devices over days, with real Wi-Fi conditions
  (`python -m idps listen --record data/raw/baseline.jsonl --label normal`).
* Controlled, *authorised* attack runs in an isolated lab (command-topic
  flooding with an MQTT client, client-id takeover, deauthentication against
  your own AP), with timestamps recorded for labelling.
* Evaluation with `python -m idps evaluate --data <labelled capture>`, plus
  a train/test split by *time* and by *device*.
* A false-positive study over long benign runs. This is the metric that
  decides whether `prevent` mode is usable.
